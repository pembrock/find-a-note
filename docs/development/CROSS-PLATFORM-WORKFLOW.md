# DEV-01 · Разработка на Windows и macOS

Windows amd64 — основная среда разработки. MacBook Apple Silicon нужен для
работы с macOS и нативной приёмки. Оба компьютера используют отдельные клоны
одного репозитория GitHub. Для каждой задачи создавайте одну feature-ветку от
актуальной `origin/main` и передавайте её между машинами через GitHub.
Постоянные ветки по операционным системам не нужны.

Команды ниже используют пример `feature/ear-training`. Выполняйте их
по этапам, из корня клона, проверяя результат каждой команды. Push, открытие
PR и слияние выполняет владелец либо Codex с явным разрешением на соответствующее
действие. [Правила Codex](../../AGENTS.md) · [Установка инструментов](../../README.md)

## 1. Начать на Windows

Проверьте рабочее дерево и получите текущую `origin/main`. Если есть
незакоммиченные изменения, сначала выберите способ их сохранения из раздела
ниже. Параметр `--no-track` оставляет upstream свободным до первой публикации
feature-ветки.

```powershell
git status --short --branch
git fetch origin
git switch --no-track -c feature/ear-training origin/main
git rev-parse HEAD
wails dev
```

Остановите `wails dev` перед Playwright. Прогоните Windows-проверки в
PowerShell. Установите Microsoft Edge для Playwright и WebView2 Runtime
для настольного приложения. Сборка frontend создаёт `frontend/dist` для Go.

```powershell
Push-Location frontend
npm.cmd ci
npm.cmd run build
npm.cmd test
npm.cmd run test:ui
Pop-Location
go test ./...
go vet ./...
wails build -platform windows/amd64
```

При изменениях настольной интеграции запустите собранный EXE и проверьте
сценарий в WebView2. Если затронуты упаковка или обновление, используйте
`./scripts/build-release.ps1 -RunChecks` для тестовых Setup и Portable.
Проверяйте обычную установку, обновление и откат на изолированных копиях
с отдельными профилями. [Упаковка Windows](../RELEASE-01.md) · [Обновления](../UPDATE-01.md)

Перед передачей добавьте только относящиеся к задаче файлы. Замените
`path/to/changed-file` реальным путём и повторите `git add` для нужных файлов.

```powershell
git status --short
git add -- path/to/changed-file
git diff --cached --check
git diff --cached
git commit -m "Add the shared ear training mode"
git fetch origin
git push -u origin feature/ear-training
git rev-parse HEAD
```

Сообщите, что ветка передана, укажите SHA, результаты Windows и сценарии,
которые надо проверить на Mac. С этого момента продолжайте редактирование
ветки на MacBook.

## 2. Продолжить на MacBook

В существующем клоне откройте ветку. Если клона ещё нет, сначала получите
репозиторий с GitHub и перейдите в его каталог.

```bash
git clone https://github.com/pembrock/find-a-note.git
cd find-a-note
```

```bash
git status --short --branch
git fetch origin
git switch --track origin/feature/ear-training
git rev-parse HEAD
```

Если локальная ветка уже есть, после `git fetch origin` используйте
`git switch feature/ear-training` и
`git merge --ff-only origin/feature/ear-training`. Сверьте HEAD с SHA
передачи. Если fast-forward невозможен, разберите расхождение перед работой.

Проверьте локальную среду Apple Silicon (`uname -m` выводит `arm64`),
Xcode Command Line Tools и `wails doctor`. Выполните команды из корня клона.
Playwright устанавливает версии браузеров, соответствующие lock-файлу.

```bash
(
  set -e
  cd frontend
  npm ci
  npm run build
  npm test
  npx --no-install playwright install chromium webkit
  PLAYWRIGHT_BROWSER=chromium npm run test:ui
  PLAYWRIGHT_BROWSER=webkit npm run test:ui
)
go test ./...
go vet ./...
CGO_ENABLED=1 wails build -platform darwin/arm64
open build/bin/find-a-note.app
```

Убедитесь, что проверки frontend прошли, прежде чем запускать Go-команды.
Для изменения DMG соберите его по инструкции MAC-04A и проверьте монтирование,
установку через Finder, запуск и поведение Gatekeeper на тестовой копии.
Для изменений updater используйте изолированные версии и профили, проверьте
успешное обновление, перезапуск и восстановление прежней версии.
[Упаковка macOS](../macos/MAC-04A-DMG-DESIGN.md) · [Обновление macOS](../macos/MAC-06B-AUTO-UPDATER.md)

Исправляйте macOS-специфичные проблемы в этой же feature-ветке. Повторите
затронутые проверки, добавьте нужные файлы и передайте ветку назад. При
отсутствии изменений достаточно передать SHA и результаты без нового коммита.

```bash
git status --short
git add -- path/to/changed-file
git diff --cached --check
git diff --cached
git commit -m "Handle the macOS-specific behavior"
git fetch origin
git log --left-right --oneline HEAD...origin/feature/ear-training
git push origin feature/ear-training
git rev-parse HEAD
```

## 3. Вернуться на Windows и открыть PR

С чистым рабочим деревом получите коммиты MacBook. Сверьте HEAD с SHA
передачи и повторите Windows-проверки из первого этапа, включая нативные
сценарии, затронутые исправлениями.

```powershell
git status --short --branch
git fetch origin
git switch feature/ear-training
git merge --ff-only origin/feature/ear-training
git rev-parse HEAD
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
```

Откройте PR из feature-ветки в `main`. Укажите изменения, результаты локальных
проверок с SHA и ограничения. GitHub Actions запускает `Cross-platform build`
после открытия PR и при обновлении его ветки. Обычный push в feature-ветку
до открытия PR не запускает этот workflow. В PR обе платформы могут собирать
синтетический merge commit GitHub. Дождитесь успеха Windows, macOS и задания
проверки общего архива. После нового коммита принимайте результат нового
прогона для актуального HEAD. [CI-01](../ci/CI-01-CROSS-PLATFORM-BUILD.md)

После ревью и требуемой нативной приёмки владелец может выполнить обычное
слияние PR через **Create a merge commit**. Проверьте новый прогон
`Cross-platform build` по событию `push` на `main` и сверьте его SHA с merge
commit. Для обновления локальной `main` на каждой машине при чистом дереве
выполните `git fetch origin`, `git switch main` и
`git merge --ff-only origin/main`.

## Незакоммиченные изменения, расхождения и worktrees

- **Передача незавершённой работы.** Если правки относятся к задаче и готовы
  к передаче, проверьте diff, сделайте отдельный промежуточный коммит и
  опубликуйте его в той же feature-ветке с разрешения владельца. Укажите SHA
  и явно отметьте незаконченные проверки. GitHub синхронизирует коммиты,
  поэтому незакоммиченные файлы и stash остаются на исходной машине.
- **Локальные правки.** Если правки ещё нельзя передать или они относятся
  к другой задаче, оставьте их в текущем worktree. Для временного локального
  хранения собственных правок можно выполнить
  `git stash push -u -m "ear-training local work"`, затем проверить
  `git stash list`. Возвращаясь, примените нужную запись через
  `git stash apply --index 'stash@{0}'`, сверьте файлы и индекс.
  Кодексу следует сохранять чужие правки на месте и согласовывать любые
  операции, которые могут их удалить или перезаписать.
- **Расхождение.** При отказе fast-forward или push сначала выполните
  `git fetch origin`, затем
  `git log --left-right --graph --oneline HEAD...origin/feature/ear-training`
  и `git status --short --branch`. Определите, какие коммиты есть на обеих
  машинах. При разрешённом объединении согласованных коммитов работайте
  в чистом worktree. После `git merge origin/feature/ear-training` разберите
  конфликт по смыслу, проверьте `git diff --name-only --diff-filter=U`, добавьте
  исправленные файлы и завершите `git merge --continue`. Чтобы отказаться от
  только что начатого слияния в изначально чистом дереве, используйте
  `git merge --abort`. Повторите затронутые проверки перед передачей.
  Для конфликтов PR с `main` действует тот же порядок на feature-ветке,
  с `git merge origin/main` после согласования. Публикация выполняется
  обычным push.
- **Несколько worktrees.** Выполните `git worktree list`, чтобы увидеть
  занятые ветки. Для новой задачи из имеющегося клона после `git fetch origin`
  можно использовать
  `git worktree add --no-track -b feature/ear-training ../find-a-note-ear-training origin/main`
  вместо `git switch -c`, если ветка ещё не существует. Перейдите в созданный
  каталог и установите зависимости. Worktree имеет собственные рабочие файлы
  и индекс, но делит refs и объекты с клоном. Если ветка уже открыта в другом
  worktree этого клона, работайте в указанном `git worktree list` каталоге.
  Между двумя компьютерами синхронизируйте коммиты через GitHub. Сборочные
  результаты остаются в соответствующем дереве, а профиль настольного приложения
  может быть общим. Для тестов установки и обновления изолируйте профиль отдельно.
- **Один активный редактор ветки.** Перед началом на второй машине получите
  опубликованный SHA и результаты проверок первой. Завершив правки, передайте
  новый SHA обратно. Перед каждым push выполните fetch и проверьте историю.
  Обе машины могут проверять один SHA одновременно. Если правки нужны
  параллельно, выделите отдельную временную ветку для подзадачи и согласуйте
  её интеграцию. Пользовательские файлы, профили, ключи и сборочные артефакты
  оставляйте вне коммитов.

## Граница общего и платформенного кода

Общие правила тренировки и представление остаются в
[frontend/src](../../frontend/src), общий доступ к Wails — в
[app.go](../../app.go), управление MIDI и протокол обновлений — в общих
частях [internal/midi](../../internal/midi) и [internal/update](../../internal/update).
Тестируйте правила unit-тестами, интерфейс — Playwright, общий Go-код —
`go test ./...` и `go vet ./...`. Подключайте новые тесты к фактическим входам
проверок, включая список файлов в [frontend/package.json](../../frontend/package.json).

Логику WinMM и CoreMIDI оставляйте за существующим MIDI-интерфейсом,
платформенные настройки окна — в `platform_windows.go` и `platform_darwin.go`,
а установку обновлений — за платформенными реализациями updater. Учитывайте
суффиксы Go `_windows.go`, `_darwin.go`, `_darwin_arm64.go` и явные ограничения
`windows && amd64` и `darwin && cgo` там, где они применяются. Для NSIS и DMG
используйте действующие скрипты соответствующей платформы. Общие изменения
и независимые исправления для одной ОС удобно проверять отдельными коммитами
той же feature-ветки.

| Изменение | Как принять |
| --- | --- |
| Документация | Проверка Markdown, ссылок и соответствия командам проекта. |
| Общие детерминированные правила и UI без нативных зависимостей | Unit, Go и браузерные проверки по области изменения. Для общей функциональности нужен зелёный кроссплатформенный CI. Ручной запуск на MacBook обычно не требуется. |
| MIDI и звук | Реальное устройство и фактическое воспроизведение на каждой затронутой платформе. Для Mac проверяйте CoreMIDI, WKWebView и звук через аудиовыход. Симулированные события отчитайте отдельно. |
| Нативное окно и WebView | Проверка в собранной Wails app на затронутой ОС. На Mac проверьте затронутые действия окна и WKWebView. |
| Установка или обновление | Нативная проверка на затронутой ОС с изолированными профилями и каталогами. Проверьте сохранение версионируемых ключей `sonari.*`, калибровки, origin Wails и идентичности профиля по сценарию. |

Edge в Playwright проверяет браузерный интерфейс, а WebKit в Playwright —
движок браузера. Нативная интеграция Wails, аппаратный MIDI, реальный звук,
Finder, Gatekeeper, установка и откат проверяются отдельно.

## Пример · «Тренировка слуха»

1. На Windows создайте `feature/ear-training`. В общем frontend добавьте
   выбор режима, генерацию задания, оценку ответа, локализованные элементы
   интерфейса и вызов существующего аудиослоя. Сохраните совместимость
   настроек и прежнего режима чтения нот. Покройте правила unit-тестами,
   а запуск задания, повтор ноты и результат — Playwright.
2. На Windows прогоните стандартные команды. В собранной Wails app
   подтвердите воспроизведение, повтор ноты и поведение выбранного аудиовыхода.
   Если режим принимает физический MIDI, проверьте ответ на подключённом
   устройстве отдельно. Закоммитьте и передайте SHA через feature-ветку.
3. На MacBook получите тот же SHA. Выполните Chromium, WebKit и
   сборку arm64. В WKWebView проверьте первый запуск звука после действия
   пользователя, повтор, громкость и сохранение настроек после перезапуска.
   Для MIDI-ответов проверьте физический CoreMIDI-ввод. Если обнаружится
   macOS-специфичная ошибка, исправьте её в той же ветке и передайте новый SHA.
4. На Windows получите обновлённую ветку, повторите Windows-проверки и
   откройте PR. Дождитесь трёх успешных CI jobs для актуального изменения.
   Режим готов к слиянию после ревью, успеха CI и подтверждения нативных
   сценариев звука и любого затронутого MIDI на обеих платформах. После
   разрешённого merge подтвердите успешный push-прогон на `main`.
